## Schema and retention safeguards

Index/retention proposals are detailed in DATABASE_SCHEMA_AUDIT.md, not applied code. No User.otpExpiresAt TTL (would delete account), no GameSession TTL without durable attempt/evidence ledger, no QR-expiry document deletion or recovery-lease TTL. Sparse unique nulls/string-vs-ObjectId partial keys/canonical aliases require explicit synthetic cases before deployment design. Installed indexes and query plans must be verified, not inferred from schemas. No actual database migration is part of Phase F.

Rollback must not resurrect tokens, consumed OTPs, attempts or redeemed prizes. Use scoped synthetic snapshots/receipts, no production restoration. Any drop/reset of even the sandbox requires explicit cleanup permission and exact checked target, not a wildcard/recursive command or “test”-looking name. Do not deploy an old application version that ignores new security fields as a rollback strategy.

Record source/tool/runtime/index manifest, seed hash, synthetic command/revision/record identifiers, status distributions and sanitized failure evidence. Keep credentials/OTP/QR/JWT bodies out of artifacts.

For each stage return PASS/WARNING/BLOCKED, exact files/commands approved and executed, accepted/rejected/failed assertions, invariants before/after, outstanding migration/security decisions and next-stage approval needs.
